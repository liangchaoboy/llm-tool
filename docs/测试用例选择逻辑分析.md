# 测试用例选择逻辑分析

## 一、问题场景

**场景**: 测试用例文件中有400个测试用例，但并发测试时设置了500个总请求

**示例配置**:
- 测试用例总数: 400个
- 并发数: 100
- 每并发请求数: 5
- 总请求数: 100 × 5 = 500

### 2.2 selectTestCase 函数

**文件**: `internal/tester/performance.go:254-279`

```go
func (pt *PerformanceTester) selectTestCase(requestIndex int) TestCase {
    // 实现 thinking:non-thinking = 1:4 的比例
    // 每5个请求中，1个是thinking，4个是非thinking

    // 统计thinking和non-thinking用例
    var thinkingCases []TestCase
    var nonThinkingCases []TestCase

    for _, tc := range pt.testCases {
        if tc.Type == "thinking" {
            thinkingCases = append(thinkingCases, tc)
        } else {
            nonThinkingCases = append(nonThinkingCases, tc)
        }
    }

    // 根据索引选择用例
    if (requestIndex%5) == 0 && len(thinkingCases) > 0 {
        // 选择thinking用例
        return thinkingCases[(requestIndex/5)%len(thinkingCases)]
    } else {
        // 选择non-thinking用例
        return nonThinkingCases[(requestIndex%len(nonThinkingCases))%len(nonThinkingCases)]
    }
}
```

## 三、行为分析

### 3.1 用例循环使用

**关键机制**: 使用模运算（%）实现循环选择

1. **Thinking用例选择**:
   ```go
   caseIndex = (requestIndex/5) % len(thinkingCases)
   ```
   - 每5个请求中选择1个thinking用例
   - 使用模运算循环使用thinking用例列表

2. **Non-thinking用例选择**:
   ```go
   caseIndex = (requestIndex % len(nonThinkingCases)) % len(nonThinkingCases)
   ```
   - 每5个请求中选择4个non-thinking用例
   - 使用模运算循环使用non-thinking用例列表

### 3.2 实际行为示例

假设：
- 测试用例总数: 400个
- Thinking用例: 80个（每5个中有1个）
- Non-thinking用例: 320个（每5个中有4个）
- 总请求数: 500个

**用例选择模式**:
```
请求 0:   Thinking用例 0
请求 1-4: Non-thinking用例 1, 2, 3, 4
请求 5:   Thinking用例 1
请求 6-9: Non-thinking用例 6, 7, 8, 9
...
请求 400: Thinking用例 0 (循环回到开始)
请求 401-404: Non-thinking用例 81, 82, 83, 84
...
请求 495: Thinking用例 19
请求 496-499: Non-thinking用例 176, 177, 178, 179
```

### 3.3 用例使用统计

**500个请求的用例分布**:
- Thinking请求: 500 / 5 = 100个
- Non-thinking请求: 500 × 4 / 5 = 400个

**用例使用次数**:
- 每个Thinking用例平均使用: 100 / 80 = 1.25次
- 每个Non-thinking用例平均使用: 400 / 320 = 1.25次

**分布特点**:
- ✅ 用例会被循环重复使用
- ✅ 保持 1:4 的 thinking:non-thinking 比例
- ✅ 用例分布相对均匀（使用模运算）

## 四、潜在问题

### 4.1 问题：并发worker的用例选择

**当前实现**:
```go
for j := 0; j < pt.config.RequestsPerWorker; j++ {
    testCase := pt.selectTestCase(j)  // j是worker内部的索引
}
```

**问题**:
- 每个worker都从索引0开始选择用例
- 如果有100个并发worker，每个worker的5个请求都会选择相同的用例序列
- 这会导致某些用例被过度使用，而某些用例可能不被使用

**示例**:
- Worker 0: 请求 0-4 → 用例 0, 1, 2, 3, 4
- Worker 1: 请求 0-4 → 用例 0, 1, 2, 3, 4（相同！）
- Worker 2: 请求 0-4 → 用例 0, 1, 2, 3, 4（相同！）
- ...

**影响**:
- 用例分布不均匀
- 某些用例可能被测试100次，而某些用例可能不被测试

### 4.2 改进建议

**方案1: 使用全局请求索引**

```go
var globalRequestIndex int64
for j := 0; j < pt.config.RequestsPerWorker; j++ {
    currentIndex := int(atomic.AddInt64(&globalRequestIndex, 1) - 1)
    testCase := pt.selectTestCase(currentIndex)
    // ...
}
```

**方案2: 使用worker ID + 请求索引**

```go
for j := 0; j < pt.config.RequestsPerWorker; j++ {
    requestIndex := workerID * pt.config.RequestsPerWorker + j
    testCase := pt.selectTestCase(requestIndex)
    // ...
}
```

## 五、总结

### 5.1 当前行为

✅ **用例会被循环重复使用**:
- 当请求数超过用例数时，用例会通过模运算循环使用
- 400个用例可以支持任意数量的请求

✅ **保持比例**:
- 保持 1:4 的 thinking:non-thinking 比例

⚠️ **并发问题**:
- 每个worker都从用例0开始，导致用例分布不均匀
- 需要改进以使用全局请求索引

### 5.2 回答您的问题

**如果测试用例中只有400个案例，并发测试时设置500个总请求，结果会如何？**

1. ✅ **用例会被循环使用**: 前400个请求使用所有用例，后100个请求会重复使用前100个用例
2. ✅ **比例保持**: 仍然保持 1:4 的 thinking:non-thinking 比例
3. ⚠️ **分布可能不均匀**: 由于并发worker都从索引0开始，某些用例可能被过度使用

### 5.3 建议

1. **确保用例数量充足**: 建议用例数量 >= 总请求数，以获得更好的测试覆盖
2. **改进用例选择逻辑**: 使用全局请求索引，确保用例分布均匀
3. **监控用例使用**: 可以添加统计功能，监控每个用例的使用次数
